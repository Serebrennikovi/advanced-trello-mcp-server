# Task Decomposition Guide

Этот гайд нужен для разбиения работы на задачи без размытого scope.

---

## Принцип

Одна задача должна отвечать на вопрос: “какой наблюдаемый результат появится после ее завершения?”

Хорошие примеры для этого репозитория:

- восстановить конкретную группу action-tools
- добавить отдельный tool для чтения комментариев карточки
- синхронизировать `ARCHITECTURE.md` с кодом
- перенести fork/main на актуальный upstream baseline

Плохие примеры:

- “разобраться с actions”
- “починить документацию вообще”

---

## Рекомендуемый шаблон задачи

```markdown
# TNN_title

## Контекст
## Что делаем
## Что не делаем
## Файлы / модули
## Acceptance criteria
## Верификация
## Какие документы обновить
```

---

## Специфика этого репозитория

Если задача касается tool-set, acceptance criteria должны включать:

1. точный count tool-ов после изменений
2. список tool names
3. результат `npm run compile`
4. обновление docs, если изменились counts или claims

Если задача касается синка с upstream, acceptance criteria должны включать:

1. какие commits подтянуты
2. какие локальные изменения сохранены
3. какие конфликты решены вручную
4. изменился ли API surface
