# Specifications Guide

Этот гайд нужен, чтобы новые спеки по проекту были короткими, проверяемыми и привязанными к реальному коду.

---

## Когда нужна спецификация

Спека нужна, если меняется хотя бы одно из этого:

- API surface сервера
- состав и semantics MCP tools
- структура модуля `src/tools/*`
- contracts входных параметров или форматов ответа
- поведение reliability layer
- root docs (`README.md`, `ARCHITECTURE.md`) как часть deliverable

---

## Рекомендуемая структура спеки

```markdown
# SNN_title

## Контекст
## Проблема
## Цель
## Не-цели
## Изменения по файлам
## Изменения по tool-set
## Acceptance criteria
## Верификация
## Документы, которые нужно обновить
```

---

## Что особенно важно для этого репозитория

### 1. Явно перечислять tool-ы

Если работа касается tools, в спецификации должен быть точный список:

- какие tool-ы добавляются
- какие удаляются
- какие считаются историческими, но уже отсутствуют

### 2. Отдельно описывать общие хелперы

Если планируется “рефакторинг на общие хелперы”, нужно прямо писать:

- какие helpers уже есть в `src/utils/api.ts`
- какие реально используются
- какой дублирующий код должен исчезнуть

### 3. Указывать базу сравнения

Например:

- “относительно `origin/main`”
- “относительно монолита `src/index.original.ts`”
- “относительно локальной ветки `feat/...`”

Без этого сравнение легко становится ложным.
